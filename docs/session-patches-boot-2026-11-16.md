# Reactivación de parches de sesión

El módulo `nemotron-session-patches` no reemplaza archivos en `/system`; su hook `boot-completed.sh` espera a que Android haya terminado de arrancar y KernelSU esté activo. Guarda los tres candidatos en `/data/adb/nemotron-session-patches`, valida SHA-256 de cada candidato y APK original, y usa montajes en el namespace de Zygote para One UI Home, HoneyBoard y System UI. Mantiene intactos los ajustes de ahorro y no ejecuta reinicios del teléfono.

El parche de System UI se intenta con un mecanismo de reversión: crea una marca de fallo antes del montaje, inicia una vigilancia y restaura el APK original si System UI no supera las comprobaciones. La versión local impide reintentar tras un fallo hasta revisión manual mediante `/data/adb/nemotron-session-patches/systemui-failed`. Para desactivar las reactivaciones se puede crear `/data/adb/nemotron-session-patches/disabled` o desactivar el módulo desde KernelSU antes del siguiente arranque.

Los archivos y hashes de los tres candidatos se copiaron y verificaron en el A54. Una ejecución manual con los tres parches ya montados informó `already_active`, `already_active`, `systemui_already_active` y no reinició System UI. **No se ha probado un arranque real ni el escenario de recuperación.** El teléfono se desconectó de ADB antes de instalar el último cambio local de protección persistente: el archivo instalado todavía usa la marca ligada al identificador del arranque. No reiniciar hasta actualizarlo y verificarlo. La reactivación depende de que DFRoot cargue KernelSU y ejecute los hooks al iniciar; no se ha comprobado en frío en esta configuración.

Android Auto mantiene su propio parche de sesión, aplicado al activar el tile. No se instaló el antiguo módulo de Android Auto que provocó el problema de arranque.

La actualización terminada se instala sin reiniciar con `tools/kernelsu/install-session-patches.ps1` cuando ADB y root estén disponibles. El instalador comprueba primero los hashes de los tres candidatos persistentes y la sintaxis de los scripts; reemplaza el hook y controladores, sin ejecutarlos ni reiniciar. La vigilancia detecta cambios o desaparición del proceso System UI y revierte el montaje si no supera la comprobación; la marca de fallo persiste entre reinicios. La sintaxis local se verificó con bash -n y el instalador PowerShell se analizó sin errores. No se probó la rama de montaje inicial ni el arranque real.
